01 // Overview

The project is a non-custodial peer-to-peer trading protocol for exchanging cryptocurrency without requiring either participant to transfer the full amount at once.

Instead of treating a trade as a single indivisible transaction, the protocol divides the agreed total into a sequence of smaller settlement rounds. In each round, both parties exchange only a fraction of the total value. The next round begins only after the previous transfers have been verified according to the rules of the relevant blockchains.

The purpose is to reduce counterparty exposure when a fully atomic exchange is unavailable. If one participant stops cooperating or attempts to defect, the honest participant loses at most the value exposed during the current settlement round rather than the entire trade.

02 // Core principle

For a trade divided into n equal rounds, the nominal exposure per round is:

E = V / n

Here, V is the total trade value. A trade worth 10,000 units divided into 100 rounds would therefore expose approximately 100 units at any individual step.

Increasing the number of rounds reduces the value that can be lost through a single act of non-cooperation, although it also increases latency, transaction costs and protocol complexity.

The system does not claim to make betrayal impossible. It makes betrayal bounded, observable and economically limited.

03 // Protocol operation

Two peers first negotiate and sign a trade agreement containing:

  • the assets and total quantities being exchanged;
  • the exchange rate or price-calculation rule;
  • the number and size of settlement rounds;
  • the order in which transfers occur;
  • blockchain confirmation requirements;
  • timeout and cancellation conditions;
  • fee allocation;
  • optional collateral or security deposits;
  • the rules for resuming or terminating an interrupted trade.

The agreement is identified by a cryptographic hash and signed by both participants. Every subsequent settlement message references that agreement and includes a monotonically increasing round number.

A simplified settlement sequence is:

TRADE_NEGOTIATED
        |
        v
CONTRACT_SIGNED
        |
        v
ROUND_1_ASSET_A_SENT
        |
        v
ROUND_1_ASSET_A_CONFIRMED
        |
        v
ROUND_1_ASSET_B_SENT
        |
        v
ROUND_1_ASSET_B_CONFIRMED
        |
        v
ROUND_2
        |
       ...
        |
        v
TRADE_COMPLETED

If a required transfer or confirmation does not occur before its deadline, the state machine stops. No later rounds are executed.

04 // Network architecture

The system is intended to operate as a decentralized protocol rather than a custodial exchange.

Peers may publish signed offers to a distributed order-discovery network. Matching peers communicate directly and negotiate the final contract without depositing assets with a central operator.

Tor can be used as an optional transport layer for:

  • peer discovery;
  • order propagation;
  • negotiation;
  • transaction coordination;
  • hiding participants’ network addresses.

Tor protects network-layer metadata, but it does not automatically hide public blockchain activity. Transaction amounts, timing patterns, address reuse and repeated settlement intervals may still make related transfers correlatable. Privacy therefore has to be considered independently at the transport, protocol and blockchain layers.

05 // Settlement modes

Native atomic settlement

Where both blockchains support compatible atomic-swap primitives, each settlement round can itself be atomic. This provides the strongest guarantees.

Progressive unilateral settlement

Where atomic swaps are unavailable, transfers alternate according to the signed schedule. Exposure is limited to one round, but one participant must still move first during each round.

Collateralized settlement

Both parties lock collateral before trading. A participant who abandons the trade or violates the signed schedule risks losing some or all of that collateral.

Collateral can reduce effective exposure below the value of one settlement round:

Lmax = max(0, E - C)

Here, E is round exposure and C is recoverable collateral.

Channel-based settlement

For assets supporting payment channels or equivalent off-chain mechanisms, many fractional transfers can occur without publishing every round as a separate on-chain transaction. This can substantially reduce fees and settlement time.

06 // Security model

The protocol assumes that either participant may become dishonest, disappear, delay settlement or attempt to exploit favorable price changes.

It therefore aims to provide:

  • bounded counterparty exposure;
  • authenticated and signed negotiation;
  • deterministic state transitions;
  • replay protection;
  • strict round numbering;
  • transaction verification;
  • configurable confirmation thresholds;
  • timeout-based termination;
  • optional collateral;
  • minimal or no third-party custody;
  • recoverable local state after interruption.

The implementation should treat all peer messages as untrusted input. Trade messages must be signed, validated against the active contract and rejected when they refer to an invalid state transition.

A peer must not be able to skip rounds, reuse an old transaction, modify the agreed quantities or persuade another node to continue from an inconsistent state.

07 // Economic considerations

Very small settlement rounds reduce fraud exposure but increase fees and latency. The protocol should therefore allow users to choose a risk budget rather than requiring a fixed number of rounds.

For example, a participant might specify:

Maximum acceptable counterparty exposure: 50 EUR

The software could then calculate an appropriate round size based on:

  • total trade value;
  • network fees;
  • expected confirmation time;
  • collateral;
  • asset volatility;
  • minimum transferable amount.

The optimal settlement schedule balances security against practical execution cost.

08 // Market-risk controls

Fractional settlement introduces a risk that one participant stops trading after the market moves against them.

Possible controls include:

  • a fixed exchange rate for the complete trade;
  • a deterministic price oracle;
  • rolling price recalculation;
  • cancellation penalties;
  • locked collateral;
  • maximum settlement duration;
  • minimum completion commitments.

The price mechanism must be included in the signed contract so neither participant can change it unilaterally during execution.

09 // Reputation and identity

The protocol can remain pseudonymous while still supporting persistent cryptographic identities.

A participant may be represented by a public key rather than a legal name. Trade history, successful completion records and collateral behavior can be associated with that key.

Reputation alone is not sufficient because users can create new identities. A stronger model combines:

  • persistent public-key identities;
  • signed trade histories;
  • collateral requirements;
  • limits for new identities;
  • increasing trade capacity after successful settlements.

This makes abandoning a dishonest identity more expensive without requiring centralized identity verification.

10 // Scope

The initial project is best treated as an open protocol and reference implementation, not as a hosted brokerage.

Its main components would be:

peer identity and cryptographic signing
signed offer format
peer discovery and order propagation
trade negotiation
fractional settlement state machine
blockchain adapters
transaction verification
timeout and recovery logic
optional Tor transport
optional collateral support
audit logs and reproducible trade records

Blockchain-specific behavior should be isolated behind adapters so the settlement engine does not depend on one coin or one transaction model.

11 // Intended use cases

The protocol is particularly suited to:

  • direct cryptocurrency-to-cryptocurrency exchange;
  • illiquid or uncommon trading pairs;
  • large peer-to-peer or OTC transactions;
  • chains that cannot participate in conventional atomic swaps;
  • users who do not want to deposit the complete trade value with a centralized intermediary;
  • experimental privacy-preserving trading networks.

It is less suited to high-frequency exchange trading, where centralized matching engines and pooled liquidity provide much faster execution.

12 // Project objective

The objective is not to eliminate trust through marketing language. It is to reduce the amount of trust required at any individual moment.

The protocol converts one large counterparty risk into a controlled sequence of smaller risks. Every completed settlement round moves the trade forward, while any failure terminates the process before the remaining value is exposed.
